# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RaceCast Emitter is a Go daemon that runs on an NVIDIA Jetson (Orin NX) mounted in a race car. It captures video (USB cameras) and audio (USB mics), records them to local MP4 files, and simultaneously streams a lower-bitrate encode over a cellular modem via SRT to a remote receiver. It also reports UPS (battery) telemetry and GPS/modem signal telemetry to the receiver over the same SRT link, and receives IDR keyframe requests back from it. There is no receiver code in this repo — only the emitter side.

The target hardware is fixed: Jetson Orin NX (aarch64) with an I2C UPS module, a Quectel cellular modem (RM520N-GL) exposing NMEA over serial and managed via ModemManager/D-Bus, and USB cameras/mics identified by udev UID.

## Build & run

Requires GStreamer 1.0 (with NVIDIA Jetson hardware plugins: `nvv4l2h264enc`, `nvv4l2av1enc`, `nvvidconv`, `nvv4l2decoder`), libsrt, and CGo — this only builds/runs meaningfully on the Jetson itself (or an aarch64 environment with the same libraries and `/dev/v4l`, `/dev/snd`, D-Bus/ModemManager access).

```bash
go build -o racecast-emitter .   # build
go vet ./...                     # static check (no test suite exists)
```

Run modes (mutually exclusive flags):

```bash
./racecast-emitter                 # normal operation: record + stream per devices.yaml
./racecast-emitter --record        # recording only, no SRT streaming
./racecast-emitter --stream        # streaming only, no local recording
./racecast-emitter --debug-modem   # standalone: log-only modem diagnostics, no recording/streaming/telemetry
```

In the normal/record/stream modes, the console is taken over by a full-screen live status dashboard (see `internal/dashboard` below) rather than scrolling log lines — the log file keeps recording everything regardless.

Configuration is via `.env` (loaded at startup, see `.env.example` for all `RC_*` variables — SRT host/port/latency (no passphrase — SRT runs unencrypted inside a WireGuard tunnel to the receiver), modem NMEA port, UPS I2C address/bus, video/audio bitrates, intra-refresh period) and `devices.yaml` (declares cameras and microphones by udev UID, capture resolution/framerate/flip, and optional per-device `stream:` block). A device with no `stream:` block or `bitrate: 0` is recorded but never streamed. `devices.yaml` documents in comments how to discover UIDs (`udevadm info --query=property --name=/dev/videoX | grep ID_SERIAL`) and supported formats (`v4l2-ctl --list-formats-ext`).

There is no test suite, linter config, or CI in this repo.

## Architecture

### Process lifecycle (`main.go`)

On startup, one `pipeline.Slot` is allocated per enabled camera/microphone. A control goroutine calls `pipeline.Poll` immediately, then again (with retries at 300ms/500ms/1s/2s) whenever a udev "add" event fires — this handles devices that take a moment to become usable after being plugged in — and also on a 15s fallback ticker so a pipeline that errors out for a reason other than a physical unplug (no udev event fires) still gets retried instead of staying down for the rest of the run. A single bidirectional SRT `telemetry.Conn` (streamid `"telemetry"`) is shared for sending UPS/modem JSON payloads out (when streaming) and receiving IDR requests in; the same UPS/modem data is read and recorded locally regardless of whether streaming is on — see the Telemetry section below. `modem.WatchConnectivity` pauses/resumes all stream pipelines (not record pipelines) when the modem loses/regains internet, so recording is unaffected by connectivity. Shutdown: SIGINT/SIGTERM cancels the root context, notifies the receiver of stream closes, sends EOS to record pipelines (so MP4 muxing finalizes cleanly) while cancelling source/stream pipelines immediately, then waits for all pipeline goroutines — a second signal forces `os.Exit`.

### GStreamer pipeline model (`internal/pipeline`)

Each device (camera or mic) is a `Slot` holding up to three independent, separately-lifecycled GStreamer pipelines, connected via GStreamer `inter*` elements (`intervideosink`/`intervideosrc`, `interaudiosink`/`interaudiosrc`) rather than being one monolithic pipeline:

- **source** — always running while the device is present. Captures raw frames/samples once and `tee`s them into two named inter-channels (`rc:v rec:<name>` / `rc:v str:<name>`, and the audio equivalents), one per consumer. Inter-sinks silently drop data when no consumer pipeline is attached, so record/stream can be started or stopped independently without disturbing capture.
- **record** — reads from the record inter-channel. Video encodes H.264 into a fragmented QuickTime file (`records/<date>/video/<time>_<name>_video.mov`, `qtmux` — see the timecode note below). Audio writes uncompressed PCM to a WAV file (`records/<date>/audio/<time>_<name>_audio.wav`, `wavenc`) with a BWF `bext` timecode chunk patched in afterwards (`bwf.go`) — no encoding, and no synthetic video track. Stopped via EOS so the muxer/`wavenc` flushes.
- **stream** — reads from the stream inter-channel, encodes AV1 (video, `nvv4l2av1enc`) or Opus (audio) and sends via `srtsink` in caller mode to `RC_SRT_HOST:RC_SRT_PORT` (SRT `streamid` = `"<name>:camera"` or `"<name>:microphone"`, used by the receiver to route/label tracks). Paused/resumed (not torn down) on connectivity changes for fast recovery.

`pipeline.Poll` starts pipelines in two phases per call: phase 1 starts any missing source pipelines, phase 2 starts record/stream pipelines only for slots whose source is confirmed running — this ordering matters, don't collapse it. Within each phase, all new pipelines are started concurrently under one `StartEach` call, which briefly redirects fd 1/2 to `/dev/null` (`silenceMu`/`silence_begin`/`silence_end` in `gst.go`) to suppress noisy NVIDIA plugin stderr output during the async state change — this silencing is global and mutex-serialized, so don't add new code paths that write to stdout/stderr from a pipeline-starting goroutine without going through the same lock.

`GstPipeline` (`gst.go`) wraps a `gst_parse_launch`-built pipeline via cgo, using two distinct contexts: `controlCtx` (parent, checked only at startup) and an internal drain `ctx` (independent, so cancelling the parent context doesn't skip EOS-based MP4 finalization — only `Cancel()`/EOS/timeout ends `watchBus`). Runtime control of named elements happens via `gst_bin_get_by_name` + property/signal calls, not by rebuilding the pipeline: `SetBitrate`, `ForceIDR` (GLib signal `force-IDR`, not a property — Jetson encoders), `TrySetIntraRefresh`, `SetValve`, `GetSRTSinkStats`. Pipeline description strings that use these must name the relevant elements consistently (`avenc` for the video encoder, `aenc` for the Opus audio encoder, `srtsink` for the SRT sink) — see `build.go`. `force_idr`'s C helper checks `g_signal_lookup` before emitting `force-IDR`, since `WatchLocalStats` calls it unconditionally on every SRT (re)connect and `opusenc` has no such signal — without the check that would be a GLib-CRITICAL, not a silent no-op (unlike `gst_bin_get_by_name` returning NULL for a name that doesn't exist at all).

Pipeline description strings are assembled as plain GStreamer launch syntax in `build.go` (`BuildVideoSourceStr`, `BuildVideoRecordStr`, `BuildVideoStreamStr`, and audio equivalents). Comments there explain non-obvious buffer-format choices (I420 vs NV12, when the VIC is invoked vs `NvBufSurfaceCopy`) — read them before changing capture/encode caps, since a mismatched format silently forces a slow CPU path on the Jetson.

`BuildVideoRecordStr` stamps a SMPTE timecode (`timecodestamper source=rtc`, for DaVinci Resolve auto-sync via the `tmcd` track the muxer writes from it) immediately after `intervideosrc`, in the raw-video segment, right before this pipeline's own `nvvidconv`/NVMM conversion — not in the shared `BuildVideoSourceStr`. `timecodestamper` only accepts `video/x-raw` caps, so it can never run any later than the raw-video segment regardless of which pipeline it's in; stamping in the shared source pipeline would just add three more hops (that pipeline's own decode/convert step, the `tee`, the inter-element handoff) on top of the ones already unavoidable here (nvvidconv, the hardware encoder, `h264parse`) before the metadata reaches the muxer — for no benefit, since nothing in the source pipeline itself consumes it.

This has been verified empirically on the actual hardware (Jetson Orin NX, GStreamer 1.24.2, R39), by mirroring both pipelines with `videotestsrc`/`fakesink` in place of the camera/LiveKit and inspecting the output file's raw box structure — two findings, one confirming the design and one that changed it:
- `GstVideoTimeCodeMeta` **does** survive `nvvidconv` → `nvv4l2h264enc` → `h264parse` intact — the worry that NVIDIA's proprietary `nvvidconv` might silently drop it turned out to be unfounded on this setup.
- The muxer choice was the actual bug: **`mp4mux` silently drops `GstVideoTimeCodeMeta` and writes a video-only file** — no error, no warning, just no `tmcd` track — while **`qtmux`**, despite sharing gst-plugins-good's isomp4 code with `mp4mux`, writes it correctly. `BuildVideoRecordStr` uses `qtmux`, and the record output file extension is `.mov` accordingly (`pipeline.go`), not `.mp4`. Do not swap this back without re-verifying the same way — it will compile, link, and record without any error either way, silently breaking Resolve sync only if reverted.

Audio recording (`BuildAudioRecordStr`) uses the equivalent, audio-native mechanism instead of a video-container workaround: it writes plain PCM via `wavenc` (`interaudiosrc ! audioconvert ! wavenc ! filesink`, `.wav`), and `bwf.go`'s `injectBWFTimeReference` patches a Broadcast Wave Format `bext` chunk (EBU Tech 3285) into the file once recording stops — the same `TimeReference` mechanism professional field recorders use, and what Resolve's "Auto Sync Audio using Timecode" reads natively. This replaced an earlier approach that muxed AAC with a synthetic black H.264 video track (`videotestsrc pattern=black` + `timecodestamper` + `mp4mux`) purely so Resolve would see *something* with an embeddable timecode — `wavenc` has no bext-aware property of its own (confirmed via `gst-inspect-1.0 wavenc`: only the generic `GstTagSetter`/`GstTocSetter` interfaces, neither of which produces one), so this is a Go-side post-processing pass, not something GStreamer does natively. `activatePipeline` (`pipeline.go`) grew an `onStopped` callback specifically for this: it fires after `SetNull()` completes, i.e. once `filesink` has actually closed the file, so the audio record entry's `onStopped` can safely patch a file that's guaranteed fully written. `injectBWFTimeReference` rewrites via a temp file + atomic rename rather than loading the file into memory — a multi-hour rally recording is easily hundreds of MB to several GB. Verified against real `wavenc` output on this hardware (not just synthetic fixtures): correct chunk structure, correct `TimeReference`, and confirmed a generic reader (Python's stdlib `wave` module) still opens the patched file without issue.

The above two mechanisms only reach the **local recording** files. The **live SRT stream** (`BuildVideoStreamStr`/`BuildAudioStreamStr`) is a completely separate GStreamer pipeline carrying raw encoded bytes with no timing metadata of its own — so RaceCast-Receiver, decoding purely from what arrives over SRT, had no capture-time information at all for live video/audio (only telemetry's `"ts"` field crossed the wire, and even that wasn't read on the receiving end). `gst.go`'s `AttachTimestampPrefix` (called from `pipeline.go`'s `startEntries`, once per stream entry, right after pipeline creation and before `StartEach` starts it — must happen before PLAYING so every buffer is covered, not just ones lucky enough to arrive after) fixes this: a `GST_PAD_PROBE_TYPE_BUFFER` probe on the named sink element (`srtsink`) prepends an 8-byte big-endian UTC nanosecond (`CLOCK_REALTIME`) timestamp to every buffer right before libsrt sends it, via `gst_buffer_make_writable` + `gst_buffer_insert_memory` at index 0 (record pipelines have no `srtsink`, so this is a harmless no-op there).

**This is a wire format change both RaceCast-Emitter and RaceCast-Receiver must be deployed together for** — an old receiver talking to a new emitter gets every frame corrupted by 8 leading garbage bytes; a new receiver talking to an old emitter silently eats 8 bytes of real bitstream data instead. There's no version negotiation; this was a deliberate scope decision (single-operator deployment, not a fleet needing staggered rollout), not an oversight.

Verified empirically end-to-end on real hardware, not just by reasoning about the API: a small throwaway probe-attached test pipeline (`videotestsrc ! nvv4l2av1enc ! srtsink`, temporarily instrumented) confirmed the header survives libsrt/`srt_sendmsg` unmodified over an actual loopback SRT connection (`srtsrc ... ! fakesink dump=true` showed the exact 8 bytes, decoding to the correct current UTC time), and a second round-trip against RaceCast-Receiver's own real `SRTListener`/`GstReceiver` code confirmed decode stays intact after the header is stripped back off and that the resulting per-frame timing is plausible for a 30fps source. See RaceCast-Receiver's CLAUDE.md for what it does with the extracted timestamp.

### Local adaptive bitrate (`internal/pipeline/feedback.go`)

The audio stream pipeline (Opus, `aenc`) runs an independent ABR loop (`WatchLocalStats`) that polls `srtsink`'s cumulative `stats` property every 2s (RTT, bandwidth, packet loss — no round trip to the receiver needed) and adjusts the encoder's bitrate via `SetBitrate`. Decrease is immediate on degradation (loss > 3% or RTT > 150ms, ×0.70); increase requires 3 consecutive stable samples (loss < 0.5% and RTT < 200ms) before stepping up ×1.10, capped at the device's configured max (floor is 1/5 of max). IDR is a no-op here (`opusenc` has no `force-IDR` signal) — `ForceIDR` checks `g_signal_lookup` before emitting, so this doesn't crash, it's just meaningless for audio. `adaptBitrate`, the core threshold logic above, is shared with video — see the next section — which is why it lives here rather than being duplicated.

Video (AV1, `avenc`) does **not** use `WatchLocalStats` any more — see the shared bandwidth budget section below for why and what replaced it. `intraRefreshPeriod`-driven `TrySetIntraRefresh` (a hardware H.264/AV1 encoder feature with no Opus equivalent) still applies to video only, gated in `pipeline.go`'s `Poll` by `entry.videoOnly`.

### Shared video bandwidth budget (`internal/pipeline/bandwidth.go`)

Every camera's stream used to run `WatchLocalStats` independently, computing `modem.BitrateAdvisoryFromStats(itsOwnMax, ...)` as its ceiling with zero awareness of any other camera streaming at the same time over the same uplink — three 8Mbps cameras on a clean LTE link would each independently aim for 8Mbps, a 24Mbps aggregate demand with no relationship to what the link can carry, and each camera would discover congestion (and later, headroom to recover) on its own schedule, with no guarantee the other cameras wouldn't try to ramp back up at the same moment and immediately re-create the congestion they'd all just backed off from.

`BandwidthCoordinator` replaces this for video only (audio's combined footprint — tens to a couple hundred kbps per mic — is a rounding error next to video's multi-Mbps range, not worth the added complexity of budgeting it too):
- One shared `sharedBudget` for all cameras combined, adapted every tick (`adaptBitrate`, the same function and thresholds `WatchLocalStats` always used) from the **worst-case** loss/RTT across every currently-streaming camera — so any one camera's congestion signal backs the whole pool off, not just itself.
- The modem-tech ceiling (`BitrateAdvisoryFromStats`) is now applied to the **sum** of all cameras' configured max bitrates, not each camera's own max independently.
- Allocation (`computeAllocation`, pure and unit-tested independent of any GStreamer/cgo dependency) gives the camera marked `main: true` in `devices.yaml` (config.go's `validate()` enforces at most one) first claim on the budget, up to its own configured max — it's never paused, only floored out at its own minimum if the budget can't even cover that. Secondary cameras split whatever's left, in name order for determinism, and are **paused** (`Slot.PauseStream()`, not just driven to an unwatchably low bitrate) the moment the remaining budget can't cover their own floor — resumed (`Slot.ResumeStream()`, which also forces an IDR) as soon as it can again.
- Cameras register (`Register`, from `pipeline.go`'s `StartEach` callback, replacing the old `WatchLocalStats` call) and unregister (`Unregister`, wired through the same `entry.onStopped` hook `bwf.go`'s audio recording uses — see its own section — fired once the stream pipeline has fully stopped) as they start and stop, so a torn-down camera can't hold a stale share of the budget or skew the aggregate degradation signal.
- One coordinator instance, constructed and its `Run` loop started in `main.go` only when `doStream` (it has nothing to do in `--record`-only mode), passed through `PollOptions.Bandwidth`.

**Resolution tier, the third ABR lever** (`decideTier`/`evaluateTiers`/`changeTier` in `bandwidth.go`): once a camera has been pinned at its own bitrate floor *and* still degraded for `tierDowngradeTicks` (2 ticks, ~4s) in a row — bitrate alone isn't enough any more — its resolution is switched **live**, on the already-running pipeline, to `tierScale` (~0.65 linear, ~40% of the pixel count, `reducedResolution`). It reverts after `tierUpgradeTicks` (5 ticks, ~10s) of clean stats at the reduced tier. Slower to recover than to degrade deliberately: even though the switch itself is brief (see the measurement below), the resolution visibly changes, so a misjudged early recovery costs another visible switch to undo. Both thresholds were shortened from an original 5/8-tick pair, set when a switch was assumed to cost far more than it actually turned out to (see the measurement below) — reaching the bitrate floor at all is already a strong degradation signal on its own, worth reacting to quickly for visibility during poor reception. Note this is on top of, not instead of, the bitrate ABR's own ramp-down to the floor (`fbDecreaseFactor=0.70`/tick, ~5 ticks/~10s under sustained degradation) — the worst-case total from "link degrades" to "resolution drops" is around ~14s, not just the `tierDowngradeTicks` window alone.

The live switch relies on the Jetson AV1 hardware encoder's own DRC (Dynamic Resolution Change) support, discovered and verified on real hardware rather than assumed: `BuildVideoStreamStr` (`build.go`) places a named `capsfilter` (`resolutionCapsfilterName`, `"rescap"`) between `nvvidconv` and `nvv4l2av1enc`; `GstPipeline.SetResolution` (`gst.go`) sets its `caps` property to the new width/height and pushes a `GST_EVENT_RECONFIGURE` upstream on its sink pad — `nvv4l2av1enc` renegotiates in place (GStreamer log: `Drc detected, reconfiguring encoder`), emitting a fresh IDR/sequence header, without an error, a dropped frame, or ever touching `srtsink`/the SRT connection. `changeTier` just calls `s.gp.SetResolution(...)` and updates `s.tier` — no pipeline rebuild, so none of a camera's reactive bitrate state needs to reset either (the encoder keeps whatever bitrate it was already targeting).

This replaced an earlier implementation that tore down and rebuilt the whole stream pipeline (`Slot.replacePipeline`) for a tier switch, which necessarily also dropped and re-established the SRT connection. That approach is gone entirely — `replacePipeline` was removed as dead code once nothing needed it any more.

**Measured total glitch, end to end on real hardware — not just reasoned about**: the full-pipeline-rebuild approach above was measured at ~270ms total (~11ms sender teardown + ~250ms for the receiver to detect the drop, reconnect, and decode its first frame) before being replaced. Relinking just the encoder's input resolution live — initially set aside as "a much larger, riskier undertaking" without being tested — turned out, once actually tried on real hardware, to need nothing more than the `capsfilter`/reconfigure-event mechanism above. Measured against both repos' real code together (a real `nvv4l2av1enc` sender against RaceCast-Receiver's actual `SRTListener`/`GstReceiver`, SRT connection never dropped): **150 frames received over a 5s window spanning the switch, zero dropped, largest inter-frame gap ~63ms** — one frame's worth of jitter, not a freeze — consistent across repeated runs. The receiver's own `av1parse` caps metadata takes longer to visibly reflect the new resolution (~300ms in this test, run at `latency=200`; not root-caused further, but plausibly related to SRT's own receive-latency buffering — production runs `latency=800`, so this number could be larger there), but frames keep flowing the entire time regardless — that number describes metadata lag, not a visual interruption, and isn't the number that matters for "is the glitch acceptable."

### Telemetry (`internal/telemetry`)

A single persistent SRT connection (cgo, libsrt) carries structured JSON envelopes both ways: `internal/ups` and `internal/modem` each have a `RunStream` goroutine that builds a typed payload via `telemetry.BuildEnvelope("ups", ...)` / `BuildEnvelope("modem", ...)` — `{"ts":...,"type":...,"data":...}`, `ts` a UTC RFC3339Nano string — and calls `Conn.Send`; `main.go` registers the receive callback that dispatches `{"type":"idr","camera":"..."}` requests to the matching camera's `Slot.ForceIDR`. `Conn` redials transparently on send/receive failure — callers don't need reconnect logic — but a failed dial is only retried once per `dialBackoff` (3s): `ups.RunStream` and `modem.RunStream` share this one `Conn` and its mutex, and `srt_connect` blocks for its own multi-second timeout, so without the backoff a down receiver would make each source's next tick stall behind the other's blocking reconnect attempt.

The modem payload sends parsed GPS fields (`lat`/`lon`/`alt`/`spd`/`cog`/`hdop`/`sats`/`fix`) only — no raw NMEA text, since it's fully redundant with the parsed fields and RaceCast-Receiver forwards `data` opaquely (never parses it), so there's no consumer for the raw form. `ups.RunStream` skips a tick entirely (rather than sending zeroed values) when an I2C register read fails, and both `ups.RunStream`/`modem.RunStream` retry `Open()`/`ensureOpen()` indefinitely rather than permanently disabling telemetry over one failed attempt at startup.

Every envelope built by `BuildEnvelope` is also recorded locally: each `RunStream` owns one `telemetry.Recorder` (`envelope.go`) writing the exact same bytes sent over SRT, one JSON line per message (JSONL, matching `internal/logger`'s own file format), to `records/<date>/data/<source>.jsonl` — `gps.jsonl` for `modem.RunStream`, `ups.jsonl` for `ups.RunStream`. The recorder is named by source rather than reusing the envelope's wire `"type"` verbatim (`modem.RunStream` records to `gps.jsonl` even though the wire type stays `"modem"`) precisely so a future car-ECU telemetry source gets its own dedicated file the same way, independent of whatever its wire type ends up being called. `Recorder.Write` rotates to a new day's file automatically, mirroring `internal/logger`'s daily rotation.

`ups.RunStream`/`modem.RunStream` both take a `send bool` (`main.go` passes `doStream`): the read-and-record loop always runs whenever recording OR streaming is on (`doRecord || doStream`), matching video/audio's local recording never depending on streaming being active, but `conn.Send` is only ever called when `send` is true. This split matters specifically for `--record`-only mode: `Conn` itself doesn't know or care whether streaming is "supposed to" be active, so without gating at the call site, a `--record`-only run with `RC_SRT_HOST` still configured (e.g. left over in `.env` from a previous stream-enabled run) would silently start dialing and sending over SRT anyway — violating that flag's own documented "no SRT streaming" contract. `modem.WatchSignalStats` is started under the same `doRecord || doStream` condition, since `modem.RunStream`'s payload needs `CachedSignalStats()` populated either way; `modem.WatchKernelLog`/`WatchHealth`/`WatchConnectivity` stay gated by `doStream` alone — they manage the cellular link for streaming's benefit specifically (pausing/resuming stream pipelines, resetting a stuck data bearer) and have no role when nothing is being streamed.

### Device discovery (`internal/devices`, `internal/udev`)

Cameras/mics are matched by udev UID (from `devices.yaml`) rather than `/dev/videoN` index, because Jetson enumeration order isn't stable across reboots or USB replug. `devices.FindVideo`/`FindALSA` prefer `/dev/v4l/by-id` or `/dev/snd/by-id` symlinks and fall back to scanning with `udevadm`. `internal/udev.Listen` opens a raw `NETLINK_KOBJECT_UEVENT` socket directly (no external library) to trigger re-polling on device hotplug.

### Modem (`internal/modem`)

Talks to ModemManager over D-Bus (`godbus`) for signal quality/technology and to enable `gps-unmanaged` mode, but reads raw NMEA sentences itself from the modem's serial GPS port (checksum-validated, grouped into epochs on each `GGA` sentence) rather than going through ModemManager's location API. Subscribes to ModemManager `InterfacesAdded`/`InterfacesRemoved` signals to transparently reattach after the modem's USB device re-enumerates (its D-Bus object path and `/dev/ttyUSBx` node can both change) — see `attachModem`/`watchModemManager`. `WatchConnectivity` is what drives the stream pause/resume in `main.go`, based on `SignalQuality`/`AccessTechnologies` (radio registration) plus the health watchdog's `recovering` flag (see below); it retries `ensureOpen()` indefinitely rather than giving up if the modem hasn't shown up yet, since on the fixed target hardware it always does eventually.

`ensureOpen()`/`Open()` (serialized by `openMu`) are the shared entry point `RunStream`, `WatchConnectivity`, `WatchHealth`, and `WatchSignalStats` each poll independently — none of them owns startup ordering, they just keep calling it until the modem appears. `WatchSignalStats` is the sole caller of `GetSignalStatsCtx` outside of `--debug-modem`'s standalone diagnostics: it polls ModemManager's `SignalQuality`/`AccessTechnologies` once a second and caches the result behind `CachedSignalStats()`, which `RunStream`, `WatchConnectivity`, `WatchHealth`, and the per-camera ABR loop (`pipeline/feedback.go`) all read instead of each polling D-Bus on their own ticker — with multiple streaming cameras that used to mean several redundant round trips per second for the same two properties.

`radio_profile.go`'s `applyRadioProfile` is called from `attachModem` (backgrounded) on every attach — initial, post-re-enumeration, and post-watchdog-reset alike, since ModemManager doesn't persist `SetCurrentModes`/`SetCurrentBands` across reattaches. It shells out to `mmcli` rather than calling those D-Bus methods directly with hand-picked `MMModemMode`/`MMModemBand` bitmask integers — getting one of those wrong from memory would silently misconfigure the radio, whereas `mmcli` resolves the same human-readable names `mmcli -m any` already prints. Mode preference (`RC_MODEM_PREFERRED_MODE`, default `4g`) is low-risk since it never narrows the allowed set; band locking (`RC_MODEM_BANDS`) is opt-in and empty by default, since a lock on bands not actually deployed at a given stage leaves the modem with zero service instead of falling back.

`watchdog.go`'s `WatchHealth` is a separate concern from `WatchConnectivity`: `SignalQuality`/`AccessTechnologies` only reflect radio registration, so a modem can be "attached" per ModemManager while its data bearer is actually stuck (common after a bad handover in poor coverage) and traffic silently stops flowing. `WatchHealth` catches this by probing real reachability itself — a TCP dial bound to the modem interface's own source address against two well-known hosts, deliberately independent of the SRT receiver in `RC_SRT_HOST` so a receiver outage can never trigger a modem reset — and escalates through a soft reconnect nudge (`Modem.Simple.Disconnect`, relies on NetworkManager's autoconnect to reconnect), then a full `Modem.Reset`, with a circuit breaker (`RC_MODEM_CIRCUIT_*`) to stop it from reset-looping forever against a fault a reset can't fix — past that it just logs for manual attention. The escalation ladder itself (`decideAction`) is a pure function of (reachable, now, state) with no I/O, unit-tested in `watchdog_test.go` independent of real time or a live modem. All thresholds are tunable via `RC_MODEM_*` env vars (see `.env.example`).

Passive diagnostics — replacing a standalone shell watcher that used to run alongside the app polling `mmcli -L` and tailing `journalctl` by hand — are built into the same D-Bus/event plumbing rather than bolted on: `handleMMSignal` in `modem.go` also reacts to the `Modem.StateChanged` signal (full state-machine transitions, logged by name via `mmStateNames`) and to `Properties.PropertiesChanged` on the `Modem3gpp` interface filtered to `RegistrationState` (arg0-matched at subscription time in `Open()`, since unfiltered `PropertiesChanged` would also catch every Bearer stats update firing every few seconds and could crowd the 8-slot signal channel). `kernel_log.go`'s `WatchKernelLog` tails `journalctl -kf` for USB power/enumeration fault signatures on the modem's own bus path (from the `Device` property). `tegrastats.go`'s `logTegrastats` snapshots RAM/CPU/thermal/power draw (one `tegrastats` line, killed right after) around the same three fault moments: the modem object disappearing, reappearing, and entering the `failed` state — this is what originally helped diagnose the USB power instability, and is cheap enough to keep firing on every re-enumeration going forward. `diagnose.go`'s `RunDiagnostics` (the `--debug-modem` CLI flag) ties this together into a standalone observe-only mode: attaches to the modem, logs a periodic signal/GPS snapshot, and runs `WatchKernelLog` — but deliberately never starts `WatchHealth`, since this mode exists to watch, not to act.

`gpsclock.go`'s `publishGPSTime` feeds GPS-derived UTC time to chrony via the well-known NTP SHM refclock interface (the same shared-memory protocol gpsd/ntpd use, reimplemented directly via cgo here rather than adding gpsd as a second NMEA consumer of the same serial port) — opt-in via `RC_GPS_SHM_UNIT` (unset = disabled, since this touches system time). It's hooked directly into `readNMEALines`'s per-line loop on every checksum-valid, active (`status=='A'`) `$??RMC` sentence, publishing on every one for the life of the run rather than just the first fix — chrony's own `makestep 1.0 1` config (not managed by this repo) is what limits the actual clock *correction* to a single step on the first update and slews everything after; this code's job is only to keep feeding it accurate samples, not to decide step-vs-slew itself. This exists because the carrier board has no battery-backed RTC (see the RaceCast-Receiver conversation that motivated it): without it, system time at boot can be arbitrarily wrong until GPS acquires a fix, which won't have happened yet by the time recording starts.

### Console dashboard (`internal/dashboard`)

In the normal (record/stream, `--record`-only, `--stream`-only) run modes, `dashboard.Run` takes over the terminal with a full-screen status view redrawn in place once a second (alternate screen buffer, cursor hidden, `\033[H`+per-line `\033[K` redraw rather than a full clear each frame, to avoid flicker) — programme uptime, modem state/tech/signal, GPS fix/HDOP/satellite count, per-camera and per-microphone color-coded status (red = source not running, yellow = source only, cyan = recording *or* streaming, green = both), telemetry link, and aggregate recording/streaming flux counts, plus a "Derniers événements" panel of the last few warnings/errors. It calls `logger.SetConsoleOutput(false)` for the duration so scrolling log lines don't tear up the redraw — the JSON log file is completely unaffected, and console output is restored (along with the normal cursor/screen buffer) as soon as `ctx` is cancelled, before `main.go`'s own shutdown log lines print. All the state it reads (`modem.GetStatus`, `modem.GetNMEA`/`ParseNMEA`, `pipeline.Slot.IsSourceRunning`/`IsRecordRunning`/`IsStreamRunning`, `telemetry.Conn.IsConnected`, `logger.RecentIssues`) is a cheap, non-blocking, already-cached read — the dashboard never itself triggers D-Bus or other I/O, it just polls state the existing background pollers (`WatchConnectivity`, `WatchSignalStats`) already maintain.

### Logging (`internal/logger`)

Writes to both a daily-rotated file under `logs/<date>.log` and the console. Because GStreamer startup silencing (see above) redirects fd 1/2 to `/dev/null` temporarily, the logger dup()s the original stdout fd at `init()` time (`consoleOut`) so log output keeps appearing on the terminal even during that window.

The console stays plain colored text; the file is **JSON Lines** (one `{"ts":...,"level":...,"component":...,"instance":...,"msg":...,"run_id":...,"fields":...}` object per line), specifically so logs across every subsystem — not just the modem — are queryable with `jq` instead of ad hoc grep/regex. `component`/`instance` are auto-extracted in `write()` from the `[component]`/`[component:instance]` bracket tag that's already the convention at nearly every call site (`splitPrefix`/`splitComponent`) — call sites using the plain `Info/Warn/Error/Fatal(format, v...)` API don't need to change to get this. A handful of call sites carrying genuinely analyzable data (ABR bitrate decisions in `internal/pipeline/feedback.go`, modem state transitions and watchdog actions in `internal/modem`) use the additive `InfoFields/WarnFields/ErrorFields(component, msg, fields map[string]any)` API instead, so that data lives in real JSON fields (nested under `fields`, never flattened into the envelope) rather than only inside a formatted string. `run_id` (set once per process start in `Init()`) lets a day's file spanning several restarts be sliced to one run. Example queries: `jq -c 'select(.component=="modem")' logs/<date>.log`, `jq -c 'select(.fields.action=="reset")' logs/<date>.log`.
